涉及事件链、定时器、存档、状态机的 bug,改之前必须画完整时序图,三条链路都要跑一遍:
1. **调用链** — 谁在何时调这个函数(直接调用 + 间接回调)
2. **读档/场景恢复链** — 状态从存档哪里恢复,恢复后会不会重新触发
3. **事件触发链** — 定时器/广播/事件回调,会不会重复注册或重复触发

**Why:** 三次血泪教训:

- **拾荒者天赋(122)双倍奖励第一次(109d350)**:`buildWorkRoomLoot` 在 `map.init` 时 roll,但 `chooseTalents` 在 `map.init` 之后才调用,`hasChosenTalent(122)` 返回 false,roll 永远失败。静态分析看不出"roll 时机早于天赋选择"。
- **拾荒者双倍第二次(2026-07-06)**:`end()` 回调里先调 `site.roomEnd(true)` 再调 `_showWorkScavengerDoubleTip`,奖励页在 roomEnd 之后才读 `this.room`,拿到的还是单倍数据。静态分析觉得"roomEnd 不改 room 内容"就没事,实测打脸。
- **金医生一天问三次(2026-07-08)**:`player.start()` 重复注册永久定时器(第一层)+ `visitPlayer` 没有当天已上门锁且未持久化,读档后当天再刷一次(第二层)。我只加了 `_dayAndNightCallbackRegistered` 防重入,只挡第一层,挡不住读档重刷。chatgpt 指出必须加 `lastVisitDay` 并写入存档,两层都覆盖。

三次都是"静态分析觉得不影响,实测打脸"。静态分析只能看直接副作用,看不到运行时间接副作用(事件链、UI 读取时机、存档序列化时机、读档恢复链)。

**How to apply:**
- 涉及"完成后给奖励"/"定时触发"/"跨天事件"/"读档恢复"的流程,改前先画完整时序图:事件触发 → 状态变更 → 判定 → 发放 → UI 显示 → 存档。确认每一步的读写依赖。
- 三条链路都要在脑子里跑一遍,确认每个可能重复触发的点。
- 防重入标志只挡单点,不覆盖跨存档场景;跨存档防重入必须把状态写入存档。
- 不准用"加个 flag 挡一下"替代根因修复,这是兜底不是修根因。用户明确说过"不准给我写任何的止血或者兜底的玩意儿"。
- 特别警惕 `roomEnd`/`siteEnd`/`saveAll`/`start`/`visitPlayer` 这类会推进状态或持久化的函数,它们在调用链中的位置会改变后续读取的数据。
- 静态分析"看起来不影响"时,必须用实测或日志验证,不能直接下结论。

**与思维链预算的关系:** 简单问题(改个文案、加个字段)快速动手,不画时序图。但只要 bug 涉及触发链/存档/状态机/定时器,就必须画——这种问题静态分析必然遗漏运行时副作用,不画时序图必然返工。
